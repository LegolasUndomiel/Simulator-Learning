# Xmake-managed build layer

The repository is compiled through Xmake. The root `xmake.lua` is the single
entry point; this `xmake/` directory holds every Xmake script so that
`Simulators/` can stay strictly read-only.

## Layout

```
xmake.lua                 # top-level entry (project, modes, includes)
xmake/
  paths.lua               # ROOT / SIMULATORS / build_out() output conventions
  dependencies.lua        # lifecycle-safe, atomic dependency bootstrap helper
  toolchains.lua          # thin Windows oneAPI environment adapter
  opencourant/
    build_fortran.lua     # native job graph/compiler with per-level dependency plans
    manifest.lua          # source lists + verified Fortran module levels
    generate_manifest.py  # maintenance translator from an official Ninja graph
  simulators/             # one module per simulator, referencing read-only sources
    pbd.lua
    mujoco.lua
    peridyno.lua
    opencourant.lua
  checks/                 # link/run-check programs for the simulator targets
```

## Principles

- `Simulators/` is never written to. A simulator's Xmake description lives in
  `xmake/simulators/<slug>.lua` and references the upstream sources by path.
- All generated output goes under the root `build/` tree, scoped as
  `build/simulators/<plat>/<arch>/<mode>/{lib,obj,dep,bin}` (see `paths.lua`).
- Dependencies that upstream fetches at configure time (e.g. PBD's Discregrid /
  GenericParameters, MuJoCo's eight vendored libraries) are cloned by Xmake at
  the upstream-pinned commits into the root `deps/` tree (source-level inputs,
  not build output, so cleaning `build/` never removes them). Restores use a
  temporary checkout and publish after the requested bootstrap revision is fetched.
  Existing checkouts are accepted as-is, not forcibly locked or overwritten. Re-run `xmake f` once
  after a restore so description-time globs see the new files.
- Heavy toolchains are opt-in: default configuration loads PBD and MuJoCo only.
  PeriDyno, OpenCourant, `pypbd` and the large MuJoCo test matrix are enabled with configure options, so a
  machine does not need CUDA, oneAPI and Python just to build the C++ projects.
- Package versions are not fixed and no package lockfile is enabled. Bootstrap
  revisions are defaults for missing dependencies, not restrictions on existing
  checkouts. Review dependencies, source lists and flags when updating upstream.

### CMake/Xmake differences handled so far

All of these are build-flag level; no upstream file is modified.

| Difference | Handling |
| --- | --- |
| CMake defines `WIN32` on Windows, Xmake does not (PBD's `Utils/FileSystem.h` then pulls in `unistd.h`) | `add_defines("WIN32")` |
| MuJoCo's C sources use C11 `_Generic` (`engine_io.c`) | `/std:c11` for the C sources |
| Upstream C++ standard is C++20 | `set_languages("cxx20")` |
| UTF-8 sources are misread under MSVC code page 936 (C4819) | `/utf-8` |
| qhull exports two include roots (`libqhull_r/...` plus flat headers) | both `qhull/src` and `qhull/src/libqhull_r` |
| CMake-generated headers (`ccd/config.h`, `miniz/miniz_export.h`, PBD `Utils/Version.h`) | generated by Xmake under `build/.../xmake-generated`; the upstream source trees stay read-only |
| A static MuJoCo library needs the same export convention on its consumers | `MJ_STATIC` on the library *and* the consumer, else `MJAPI` becomes `__declspec(dllimport)` and the link fails on `__imp_mj_*` |
| MuJoCo's OBJ/STL/Gmsh decoders are source files added directly to the core target, not plugin DLLs | compile `plugin/{obj,stl,gmsh}_decoder` into `mujoco.dll` |
| MSVC release optimisation must match MuJoCo's tested CMake profile | use AVX/SIMD plus `/Oi`, `/Gy`, `/GL` and `/LTCG` |
| PeriDyno enables CUDA separable compilation only for `Topology` | disable Xmake's default RDC elsewhere; retain device-link for CUDA targets |
| PeriDyno embeds OpenGL shaders as generated SPIR-V headers | use Xmake's `glslang` package and generate under `build/simulators/peridyno/xmake-generated/shader` |
| Long PeriDyno example/source names exceed legacy MSVC object-path limits | use compact per-example object roots under `build/obj/` |
| OpenCourant needs its official Ninja-derived module graph and exact per-file flags | Native object targets express the module levels from `opencourant/manifest.lua`; a thin oneAPI environment adapter and an ifx object-only response-file link hook handle Windows compatibility. Functional parity validation is still pending. |
| ifx/icx need the oneAPI+MSVC shell environment | `oneapi-windows` reuses Xmake Visual Studio discovery and supplies Intel compiler/MKL paths under `ONEAPI_ROOT` or the standard Windows installation; it does not call `setvars.bat` |
| Official Ninja builds preprocess every Fortran file, even ones whose per-file flag overrides drop `/fpp` | keep `/fpp` on the override sets (the compiler runs it anyway) |
| OpenCourant's generated message/build-info includes | official Python scripts generate under `build/simulators/windows/x64/release/generated/opencourant/<component>/includes`; sibling `modules/` stores `.mod` files |

## Usage

```powershell
# Default: PBD + MuJoCo (without pypbd)
xmake f -P . -y -c -m release
xmake build -j12

# Add the MuJoCo unit-test and benchmark executables
xmake f -y -c -m release --with_mujoco_tests=y

# PBD Python binding (configure the interpreter explicitly if needed)
xmake f -y -c -m release --with_pbd=y --with_mujoco=y --with_pypbd=y `
  --pbd_python_root="C:/path/to/python"

# PeriDyno (CUDA architecture is configurable; 89 matches the verified host)
xmake f -y -c -m release --with_pbd=n --with_mujoco=n --with_peridyno=y `
  --peridyno_cuda_arch=89 --peridyno_cuda_sdk="$env:CUDA_PATH"
xmake build -j12 peridyno

# OpenCourant native object-target build: Windows x64 Release only
xmake f -y -c -m release --with_pbd=n --with_mujoco=n --with_opencourant=y
xmake build -j12 opencourant

xmake run pbd_link_check   # run the PositionBasedDynamics link check
xmake run mj_link_check    # run the MuJoCo core link check
xmake test "*_link_check/smoke" # run both registered smoke tests
```

`-j N` is handled by Xmake's native scheduler, with no independent per-component
worker pools. The old `XMAKE_OC_JOBS` override, `oneapi-env.lua` snapshots and
`oc_state.txt` mechanism are no longer used. An object-only response-file link
hook remains because ifx rejects `/link` inside a long-command response file.

Run examples from the repository root. If a probe configured with `-P` shadows
the root project, restore the association with `xmake f -P . -y -m release`.
Run future standalone probes from their own directory instead. `-c` resets
configuration, not compiled objects. `-a` builds only projects enabled by the
`with_*` options; enable all four explicitly for a full build.

### Build all managed projects

From the repository root (Windows x64 Release):

```powershell
xmake f -P . -y -c -m release --with_pbd=y --with_mujoco=y --with_peridyno=y --with_opencourant=y
xmake build -a -j12

# Optional: force a full rebuild rather than an incremental build
xmake build -a -r -j12
```

This covers PBD, MuJoCo, PeriDyno and OpenCourant, not Python/Rust projects.
Install MSVC, CUDA, Intel oneAPI/MKL and Python first. For MuJoCo tests append
`--with_mujoco_tests=y` to configuration; for PBD Python bindings append
`--with_pypbd=y --pbd_python_root="C:/path/to/python"`. After configuration,
reuse the build command without reconfiguring. Current OpenCourant validation
limits below still apply.

## Current validation limits

Windows is the current supported host; Linux support awaits Ubuntu testing.
OpenCourant additionally requires x64 Release, Intel compiler/MKL and Python
on PATH (or `--opencourant_python=<executable>`).

Both native OpenCourant components have built successfully. The engine run
took 1869.9 s before the performance fixes; it is not a demonstrated speedup.
The current Fortran adapter uses Xmake's global job graph and compiler interface,
but stores one conservative dependency plan per module level instead of writing
thousands of individual dependency records. It tracks source/header input lists,
preceding dependency objects and compiler flags; it does not request the
unsupported `/showIncludes` option. A large-batch test completed in 122.0 s;
the final combined forced rebuild passed in **645.0 s** with at most **12**
compiler processes. The immediate no-op passed in **18.3 s**, with no compilation
in its log. No root-level `.asm` files remained after the rebuild. Intel C/C++
uses Xmake's CL-style adapter/probe explicitly (`clang_cl@icx.exe`) to avoid the
GNU-style assembly flag probe. Module deletion/recovery, module consumer
invalidation, link-library invalidation and post-refactor miniQA remain to test
or improve. A successful no-op does not establish dependency correctness.

The MuJoCo test executables use files relative to `Simulators/mujoco/test`.
For plugin-dependent tests, set `MUJOCO_PLUGIN_DIR` to the Xmake `bin` output.
